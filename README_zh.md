# Enterprise-RAG

面向企业内部资料的检索增强问答系统。它的取舍是：凡是关于效果的说法，都要能在一份冻结的评测集上复现，而不是让人相信。

开源 RAG 项目大多比拼功能覆盖面，这个项目比拼的是数字站不站得住：检索与生成分开度量，权限过滤每次运行都做断言，被证明不成立的结论原样记录，不悄悄抹掉。

> **当前状态：** S0–S6 已完成，S7–S8 未开始。面向单机小团队场景。下文的时延与吞吐数字来自一台 Apple M4 主机，不是生产环境的服务等级承诺。

## 这个系统做什么

员工用中文或英文提问，系统只在该员工有权访问的资料范围内检索，只依据检索到的证据作答，并给出可以直接跳回原文的引用——PDF 定位到页和坐标，Word 定位到标题路径与段落，Excel 定位到工作表与单元格。依据不足，或两份规定互相矛盾时，系统会明说，而不是猜一个。

- **回答有依据。** 模型选择带编号的原文片段，服务端据编号取回真实原文、重新校验权限后才返回。引用核对不通过的答案直接不返回，不做修补。
- **权限进检索，不做事后过滤。** 访问控制在查询内部生效。迄今全部评测运行中，越权命中与隐藏文档泄漏均为 0。
- **撤权立即生效。** 决定可见性的是业务库而不是搜索索引：撤权提交之后的下一个请求，在列表、详情、解析预览、引用、原件下载和可读性探测**每一条入口**上都已被拒绝，不需要刷新、不需要等待。
- **版本替换不留空窗。** 新版本先完成索引并确认可搜索，才会切换生效；处理失败或变慢只会退化成"什么都没变"，不会变成一份空文档。被替换的版本保留在库中，供审计引用了它的旧回答。
- **解析保真。** PDF、DOCX、XLSX、Markdown 输出统一结构，保留标题层级、真实页码、版面坐标和单元格范围。Excel 公式没有缓存值时标记为缺失，不当作已算出的数值。
- **评测可复现。** 语料冻结，金标绑定到原文位置，运行器的断点与配置摘要绑定——换了快照就不可能悄悄复用上一版的结果。

## 实测结果

以下数字全部来自冻结的开发集，可用下方命令复跑。留出集从未运行，也从未查看。

### 检索侧 —— s3-v2 开发集，147 题

| 配置 | Recall@5 | Recall@10 | MRR@10 | nDCG@10 | 检索 p95 |
| --- | --- | --- | --- | --- | --- |
| BM25（cjk 分析器） | **0.984** | **0.992** | **0.927** | **0.944** | 0.04 s |
| 向量检索（BGE-M3，1024 维） | 0.903 | 0.935 | 0.840 | 0.861 | 0.23 s |
| 混合检索（倒数排名融合） | 0.935 | 0.976 | 0.900 | 0.918 | 0.26 s |

分母是 124 道带文档级金标的题；无答案题与越权探测题不计入检索指标。

混合检索在每项检索指标上都低于 BM25——一路明显强于另一路时，倒数排名融合会把强路拖向弱路。**但它仍然是默认配置**，因为检索指标在这里误判了端到端效果，见下。

### 端到端 —— s3-v2 开发集，147 题，提示词 `grounded-v5-conflict-gated`

| 配置 | 状态判断正确 | 字面事实覆盖 | 冲突召回率 | 冲突精确率 | 越权命中 |
| --- | --- | --- | --- | --- | --- |
| BM25 | 84.4% | 84.6% | 10/13 = 77% | 10/10 = 100% | 0 |
| 向量检索 | 85.0% | 82.1% | 9/13 = 69% | 9/9 = 100% | 0 |
| **混合检索（默认）** | **89.1%** | **89.1%** | **11/13 = 85%** | 11/11 = 100% | 0 |

混合检索取得了实测最高的端到端正确率（89.1%），但在当前评测集上，相对 BM25 的提升**未达到统计显著**（McNemar 精确检验，p = 0.19，147 组配对）。选它作默认的依据是：在所有已测维度上它不是最好就是持平，没有一项更差。这里的表述是"实测最优"，不是"已证明更优"。

**文档级检索指标误判了端到端效果。** 混合检索的 Recall@5 是三者最低，回答正确率却最高。证据预算只有 4 段时，决定成败的是这 4 个槽位被谁占了，而不是金标文档在不在前 10。融合会把两路都认可的段落顶上来，预算因此花在了共识证据上。

事实覆盖是归一化后的字符串匹配，不等于人工判定的正确率。语义正确性、忠实度与引用蕴含**尚未测量**。

### 重排 —— 已实现，但默认关闭

`bge-reranker-v2-m3` 交叉编码器对融合后的前 30 个候选重新打分。它把检索指标推得很明显——Recall@5 0.935 → 0.968，MRR 0.900 → 0.935——端到端却几乎没动：状态判断正确率 89.1% → 90.5%，McNemar 精确检验 p = 0.79（147 组配对）。

保持关闭，依据与当初把混合检索设为默认时是同一条规则：**在所有已测维度上不是最好就是持平、没有一项更差，才采用**。重排不满足——冲突精确率从 100% 降到 92.3%，中位耗时上升 22%，换来的是 p = 0.79 的端到端差异。

值得记一笔：重排大幅改善了检索指标却几乎没改善答案质量，而融合恰好相反。**检索指标与回答质量之间在这里不存在单调关系**，所以两者都要测，不能拿一个当另一个的替代。

### 外部有效性 —— 公开基准固定子集，39 题

EnterpriseRAG-Bench v1.0.0，取两个已发布 github 分片中金标文档齐全的全部题目，另加 100 份干扰文档。英文语料，与自建中文集属于不同分布。

| 配置 | Recall@5 | 状态判断正确 |
| --- | --- | --- |
| BM25 | 0.897 | 33/39 = 84.6% |
| 向量检索 | 0.897 | 29/39 = 74.4% |
| **混合检索（默认）** | **0.974** | 33/39 = 84.6% |

**混合检索在这里的检索优势比在自建语料上更大**，与它在自建语料上垫底的表现正好相反。这支持了另一个判断：BM25 在自建语料上领先，来自那批文档高度可区分的专有名词，而不是词项检索本身的普遍优势。

字面事实覆盖在这份数据上**不适用**，因此标为不适用而不是报一个数字：上游金标是散文，模型的答案措辞不同但语义正确，而为中文短值设计的子串匹配在这种情况下恒为接近零，与正确与否无关。

这份子集测的是外部有效性，不是统计功效。它的题目来自不同总体，绝不并入上文的显著性检验。

### 多轮追问 —— 40 组会话 / 160 轮

「那请求超时呢？」这类追问不带主语，单轮检索必然失败。改写的作用是驱动检索，因此四组对照只测检索。

| 组 | 整体 R@5 | 追问 R@5 | 指代 R@5 | 条件保真 | 换题污染 | 改写耗时 |
| --- | --- | --- | --- | --- | --- | --- |
| A 不改写 | 0.825 | 0.650 | 0.150 | 100% | 0% | 0 s |
| **B 拼接上一轮提问（已采用）** | **0.988** | **0.975** | **0.900** | **100%** | **0%** | **0 s** |
| C LLM 改写、无历史 | 0.825 | 0.650 | 0.150 | 100% | 0% | 2.70 s |
| D LLM 改写 + 最近 3 轮 | 0.944 | 0.900 | 0.850 | 95% | 2.5% | 4.51 s |

**收益全部来自历史，没有一点来自"用模型改写"。** C 组与 A 组每一项都完全相同——没有历史，就没有任何东西可以用来消解省略。零模型调用、零延迟的规则直接胜过了 LLM 改写；而 LLM 变体还挂在两条硬门槛上：一例把用户说的数值整个丢掉，另一例把一个全新话题的提问改写回了上一轮的主语。

空历史时该规则是恒等操作，因此上文全部单轮结果继续有效。

### 失败归因

修复前的基线共 86 次失败，其中**只有 6 次（7%）是没检索到资料，80 次（93%）发生在正确资料已经被检索到之后**。所以工作顺序是先处理回答状态的判定逻辑，再谈召回优化。

### 这套评测抓到的一个缺陷

冲突判定原本是第二次模型调用，返回一个布尔值就直接覆盖回答状态，不需要任何可核验的依据。结果它在 120 道题里触发了 24 次，而真正的冲突只有 1 道——**精确率 4.2%**。

修复方式是加门槛：必须给出分属两份不同文档、且互相矛盾的两个原文编号，否则不允许改状态。精确率升到 100%，状态判断正确率提升约 19 个百分点。

当时无法测量召回率：冻结的 v1 只有 1 道冲突题。v2 为此补了 12 道真冲突和 15 道易误判反例——不同指标、不同适用对象、有明确先后的新旧版本，以及跨文档数值不同但并不矛盾的成对资料。在这份数据上，加了门槛的冲突判定达到 **85% 召回、100% 精确**，15 道反例无一误报。

## 系统结构

```text
入库   上传 → 鉴权 → 保存不可变原件 → 解析 → 分块 → 向量化
       → 写入待发布索引 → 确认可搜索 → 切换活动版本

问答   识别身份 → 在授权版本范围内检索 → 融合 → 复查版本与授权
       → 组织证据 → 生成 → 校验引用 → 再次鉴权 → 返回答案与原文位置
```

| 层次 | 选型 | 理由 |
| --- | --- | --- |
| 接口 | Python、FastAPI、Pydantic | 数据结构明确；评测复用同一套检索代码 |
| 业务库 | PostgreSQL、SQLAlchemy、Alembic | 存身份、授权、版本、任务与回答溯源 |
| 检索 | OpenSearch，BM25 与向量同一后端 | 统一分块 ID、统一过滤条件、统一更新路径 |
| 解析 | Docling，单元格定位辅以 openpyxl | 不自研解析模型，但自己掌握结构与来源信息 |
| 向量模型 | BGE-M3（`bge-m3:567m`），仅用 dense 输出 | 可复现，对中文与英文标识符都够用 |
| 生成模型 | Qwen2.5 7B Instruct，经 Ollama 走 Metal | 固定随机种子与温度，保证各轮可比 |
| 异步任务 | PostgreSQL 任务表，含租约与重试 | 首版不引入消息中间件 |
| 前端 | React、TypeScript、PDF.js | 资料状态、证据抽屉、检索调试三类界面 |

## 复现评测

```bash
make test              # 88 项单元与逻辑检查（集成类需要开关）
make integration       # 真实数据库、权限与任务恢复检查
make s3-validate       # 用解析出的原文审计金标
make s3-freeze         # 固定输入哈希与模型摘要
make s3-retrieval      # BM25 / 向量 / 混合三路检索指标
make s3-generate       # 端到端答案、引用与失败分类
```

有四条约束是由程序强制的，不靠自觉：

1. 金标只进入评分环节，绝不进入检索、提示词、改写与缓存。
2. 最终评测之前，`--split holdout` 直接拒绝执行。
3. 断点记录绑定配置摘要，跨快照续跑会立即报错。这条规则抓到过一次事故：新语料的运行静默复用了旧语料的结果，指标一模一样。
4. 新增评测材料不得触碰现有语料已经回答过的事项。对一个已有定论的事项再加一份"另一种说法"，等于把原本正确的金标变成错的。

## 已验证与未验证

把这两份清单混为一谈，是 RAG 评测最常见的误导方式，所以这里分开列。

**已验证，产物在 `artifacts/`**

- 四种格式解析出可检查的结构与原文位置，54 项检查通过、0 跳过。
- 20 道开发题在一次完整浏览器回归中全部满足预期，连同上传与格式检查共 23/23。
- 引用身份：返回的每条引用都能对应到存储的原文、版本与位置。
- 权限过滤：全部运行中越权命中与隐藏文档泄漏均为 0。
- 重启恢复：原件、授权、版本、分块与向量在整栈重启后保持一致。

**未验证**

- 语义正确性、忠实度、引用蕴含——目前只有字面匹配。
- 留出集——80 题，从未运行，也从未查看。
- 金标的独立人工复核——记为 **0**。程序审计能证明某个事实确实写在它自己的来源里，但证明不了这道题问得合理、答案标得对。

## 已知限制

1. 不支持扫描件与 PPTX；没有文字层的 PDF 会明确报错，不会静默入库成空内容。
2. 混合检索作为默认，依据是实测最优而非统计显著。公开基准子集已运行且结论一致；留出集在最终验收前保持封存，是判定显著性的预定手段。
3. PDF 页内高亮已覆盖全部语料：用旧解析器入库的 33 份资料已通过版本替换重新处理，用时 45 秒，33 份全部切换成功。
4. 不做工作记忆，也不做长期记忆。`/api/chat` 仍然无状态；客户端可以回放用户自己写过的提问，用于把追问补全成可检索的查询——仅此而已，可读文档集合始终按当前用户重算，回放的文本不授予任何权限。落库的问答历史只用于审计与复查，不回灌给模型。
5. 冲突判定在 13 道真冲突与 15 道反例上实测 85% 召回、100% 精确。仍有 3 道漏判，且样本量偏小。
6. 面向单机演示。速率限制、备份、TLS、多机部署与并发余量都不在首版范围内。
