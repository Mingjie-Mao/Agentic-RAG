Traffic escrow and rehearse proxy for staged promotes

Motivation:
We frequently observe that promotes that look good on telemetry during a short canary window still cause edge-case regressions once given full traffic. This PR introduces two complementary primitives: (1) a traffic_escrow service that holds routing decisions and only releases commits once a rehearse pass and smoke policy succeed, and (2) a rehearse_proxy that can inject synthetic canary traffic and replay recorded request traces into candidate serving revisions without affecting production state.

Goals:
- Allow operators to stage promotes with a commit escrow lease that requires an endorsement from rehearse results before full cutover.
- Provide a reproducible, auditable rehearse run that exercises session affinity, header routing, and KV cache warmup without serving user writes to production.
- Reduce time-to-revert via an escrow ledger that records the include/exclude criteria, lease owner, and rehearse outcomes per promote.

What this PR contains (single-string description):
Implemented a TrafficEscrow controller, a RehearseProxy sidecar + router middleware, a small replay harness for synthetic canaries (replay driver + sampler), and related observability (metrics, traces, and a prometheus scrape target). Included an admin API to grant/revoke escrow leases and an operator CLI hook to trigger a rehearse run. The rehearsals are configurable with smoke policies and timeout/rollback thresholds.

Small illustrative snippet (rehearse proxy header handling):

func (rp *RehearseProxy) ServeHTTP(w http.ResponseWriter, r *http.Request) {
    if rp.isRehearseRun(r) {
        // tag and route to candidate revision; keep responses sandboxed
        r.Header.Set("X-Rehearse-Run", rp.currentLeaseID)
        rp.routeToCandidate(w, r)
        return
    }
    rp.routeNormal(w, r)
}

Operational notes:
- Default behavior is a no-op until rollout.traffic_escrow is enabled.
- The escrow ledger keeps soft TTLs for leases; expired leases auto-fail after the configured grace period.
- Rehearse runs can be run in parallel for non-overlapping cohorts; controller rejects overlapping leases by default to avoid double-warmup.

Why this is different from existing rollout features:
This PR focuses on the concept of escrowed commits plus a rehearse proxy that allows routing and replay isolation so that candidate revisions can be exercised end-to-end without touching production state. Existing staged promote primitives at Redwood emphasize traffic phasing and shadowing; traffic escrow gives an operator-level commit gating primitive with a ledger and rehearsals that are auditable and replayable.
