Emit structured audit log events for Optimization Config lifecycle (create/validate/apply/promote/rollback) + schema updates

Context: Optimization config changes (batching/caching/quantization profiles) are production-impacting and must be traceable and reviewable. We’ve had gaps reported by enterprise customers (SUP-18544) and internal operators (INT-3390) where rollback actions were not consistently visible in audit exports, and some lifecycle steps were only logged in app logs. This PR standardizes and emits structured audit events for the full Optimization Config lifecycle and updates the audit schema registry accordingly. What’s included: (1) New/standardized event names under the "optimization_config" namespace: optimization_config.version_created, optimization_config.version_validated, optimization_config.apply_requested, optimization_config.rollout_started, optimization_config.rollout_paused, optimization_config.rollout_resumed, optimization_config.rollout_step_completed, optimization_config.rollout_failed, optimization_config.version_promoted, optimization_config.rollback_requested, optimization_config.rollback_completed, optimization_config.rollback_failed. (2) Consistent required fields across events: event_id, occurred_at, actor_type (user|service), actor_id, actor_email (when actor_type=user), actor_roles (best-effort snapshot), source (console|api|controller), request_id, trace_id (if present), tenant_id, scope (tenant/model/region; serialized as strings), optimization_config_id, optimization_config_version_id, from_version_id/to_version_id (when applicable), rollout_id (for staged apply), canary_percent (when applicable), reason (free-form operator reason; required for rollback_requested), gate_summary (serialized compact string: "latency_p95:pass;5xx:fail" etc.), eval_run_id (only for quantization-related applies where eval gating was invoked), and outcome (success|failure) with error_code/error_message when failure. (3) Explicit PII/secret handling: the audit payload does NOT include raw config bodies, prompt data, or customer inputs; the only config-related identifiers are config_id/version_id and a small "diff_fingerprint" (sha256 of normalized diff) for correlation. (4) Event emission points: service-layer emission in Optimization Config Service for create/validate/apply/promote/rollback API endpoints; rollout controller emits step/progression and gate evaluation results; rollback controller emits completion/failure. (5) Schema updates: updated audit schema registry entries for all new events, plus tightened validation rules for required fields and enums; added forward-compatible optional fields for private deployments (cluster_id, deployment_id) without making them required. (6) Backfill/compat: kept prior legacy event names as aliases for 30 days (emitting both) behind feature flag AUDIT_OPT_CONFIG_DUAL_EMIT; Console and downstream export pipelines continue to function. Example payload (redacted): {"event_name":"optimization_config.rollback_requested","actor_type":"user","actor_id":"u_7f...","actor_email":"oncall@redwoodinference.com","source":"console","tenant_id":"t_123","scope":"model=llama-3.1-70b;region=us-east-1","optimization_config_id":"ocfg_91...","optimization_config_version_id":"v_42","from_version_id":"v_43","to_version_id":"v_42","reason":"p95 regression during canary","request_id":"req_...","trace_id":"tr_..."}. Testing/verification: unit tests for event construction and schema validation; integration tests asserting audit emission on each endpoint; controller tests verifying pause/resume and failure paths emit the right events; manual verification in staging that events appear in SIEM-export sink with correct field names. Rollout plan: ship behind AUDIT_OPT_CONFIG_EVENTS_V1 (default off); enable for internal beta tenants first; after 1 week with no schema errors in export, disable dual-emit and remove aliases in follow-up PR.
