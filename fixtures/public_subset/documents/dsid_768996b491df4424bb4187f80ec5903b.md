SLO Grace Period Manager and Ephemeral Warmup Hotfix

Context: Over the last 3 weeks we've seen transient latency spikes in several regions during short-term autoscaler churn and model warmup windows. Those spikes caused the tenant SLO enforcer to escalate to circuit state and eviction before transient load and warmup completed, resulting in customer-visible errors and unnecessary failovers. This PR introduces two coordinated fixes: 1) a SLO Grace Period Manager that tracks short-lived SLO breaches with a decaying credit window and only surfaces enforcement actions after a configurable sustained breach threshold; 2) a lightweight Ephemeral Warmup soft-weight which temporarily raises the tolerance for newly scheduled or recently-warmed backends so they aren't penalized while their KV caches and JIT paths populate.

Summary of changes: Introduces new runtime component (grace_period_manager) implemented in runtime/slo/grace_period_manager.go with a small in-memory sliding-credit store per-tenant and per-region. Adds an API hook for the enforcer to query transient breach state before flipping circuits. Adds a warmup label to node metadata and a soft-weighting function in scheduler/weighting.go that decays over a warmup window (default 30s). Adds feature-flag gate (feature.slo_grace_period) and canary rollout config (deploy/overlays/us-west-2/canary.yaml). Instrumentation: new metrics redwood.slo.grace_window_credit{tenant,region}, redwood.slo.warmup_weight, and events for grace_period_expiry and grace_period_persisted. Rolling upgrade plan: canary in us-west-2 (10% of serving fleet), monitor error-rate and activation_rate metrics for 2h, then 50%/100% if safe. Backout: toggle feature.slo_grace_period=false will revert behavior immediately and flush in-memory credits on restart.

Why this approach: Previous fixes focused on aggressive eviction and conservative failover; they either tolerated bad latency for too long or acted too fast. Using a decaying credit window provides a low-cost, stateless-ish mechanism to distinguish short spikes from sustained regressions without requiring long-term historical storage. Ephemeral warmup weighting reduces false positives during normal autoscaler activity and model cold starves during scale-up.

Testing: unit tests for credit decay and xor-edge removal in runtime/slo/grace_period_manager_test.go; integration test in perf-canary harness that simulates bursty autoscaler events (tests/perf/autoscale_burst_slo_test.go). Local perf-lab run measured reduction of reactive-evictions by ~78% in synthetic warmup scenarios. CI showed one flaky e2e related to test harness timing; that test was stabilized and re-run. QA verification checklist included: canary traffic ramp, metric thresholds validated, do-not-evict tag respected.

Rollout and monitoring: Canary deploy via overlays with feature flag. Dashboard: dashboards/slo/grace-period-overview.json contains target panels. Alerts to watch: SLO.Enforcer.SustainedBreachRate > 0.5% for 10m (post-deploy), Serving.Evictions > baseline + 3 sigma. On anomalies, immediate rollback by disabling feature.slo_grace_period or scaling canary group to zero.
