Add CLI command to dump effective runtime config after hardware profile selection + overrides

Context: as we roll out the hardware tuning profiles pack + override precedence (fleet default -> per-deployment -> per-route -> env/flags), Support and SRE need a fast way to answer “what config is this runtime *actually* using right now?” without grepping logs or reverse-engineering values.yaml + env vars. This PR adds a small CLI/tooling command that prints the effective runtime config after profile selection and all overrides are applied, including the source/precedence for each key, and with safe redaction of secrets. What’s included: (1) New CLI subcommand: `redwood-runtime config dump` (alias: `redwood-runtime dump-config`) (2) Supports YAML and JSON output: `--format=yaml|json` (default: yaml) (3) Includes optional provenance: `--explain` adds a per-key “source” (profile_pack / runtime_default / config_file / env / flag / route_override) and the profile id/version chosen (4) Redaction by default: any key matching `*token*`, `*secret*`, `*password*`, `*api_key*` is replaced with `"<redacted>"`; `--no-redact` requires `--i-understand-this-prints-secrets` (5) Stability for runbooks: output is sorted deterministically and emits a single header line with runtime version, profile pack version, detected hardware, and override summary (counts by source). Example usage: `redwood-runtime config dump --explain --format=yaml` prints the config used by the running process (or from a config file via `--config /path/runtime.yaml`). Operator workflow: oncall can `kubectl exec` into a pod, run the command, and paste into incident threads; Support can ask Private customers to run the command and attach output (safe by default). Non-goals: not a full “doctor” tool; does not attempt to validate fleet health; does not persist output anywhere. Notes: This builds on the precedence rules implemented in PR-21991 and adds a single shared `EffectiveConfig` snapshot that is already used by startup logs. This PR reuses that logic rather than duplicating config resolution. Follow-ups: we may want to wire the same output into the debug endpoint added in PR-22027 so that we can fetch it remotely when permitted by policy.

Implementation details: CLI is implemented in `cmd/redwood-runtime/config_dump.go` and uses the existing config loader to compute `EffectiveConfig`. Provenance is carried by `ResolvedValue{value, source, source_detail}`; `source_detail` includes e.g. env var name or config file path. YAML output uses our existing internal serializer (no anchors) for readability in tickets. The command exits non-zero if config parsing fails; with `--strict`, it also exits non-zero if hardware detection is ambiguous (mirrors loader behavior).

Testing: unit tests cover redaction patterns, deterministic ordering, provenance output, and a golden-file test for YAML output. Added an integration test that runs the CLI in a minimal container entrypoint to ensure it can execute without GPU present (important for CI + support tooling containers).
