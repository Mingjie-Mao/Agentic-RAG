Emit rollout auto-action audit events to event stream (pause/rollback/suppress)

Summary: This PR emits structured, machine-readable audit events for rollout auto-decisions (AUTO_PAUSE, AUTO_ROLLBACK, AUTO_SUPPRESS) onto the existing audit event stream. These events are consumed by Console backend, incident-bot, and downstream retention/export tooling.

Motivation: As we wire SLO breach evaluation into the rollout controller, we need a durable and queryable record of what happened (decision, inputs, and who/what initiated it). This enables (1) Console “why did we rollback?” views, (2) incident notifications with correlation IDs, and (3) compliance/auditability expectations for Dedicated/Private customers.

What’s included: - New event type: rollout.auto_action (versioned schema v1) - Correlation IDs: propagate rollout_correlation_id across evaluator -> controller -> executor; include decision_correlation_id per decision emission - Monitor linkage: include monitor_provider + monitor_ids and monitor_definition_url (when available) for the evaluated SLOs - Policy linkage: include policy_id + policy_version (hash) used for the decision - Decision details: action (pause|rollback|suppress), scope (route/model_version/region/customer_tier), and suppression reason (admin override, incident window, telemetry stale, min sample not met) - Privacy/safety: no prompt text, no customer payloads; IDs only. Metrics are referenced via snapshot_ref (pointer) rather than embedding raw time series.

Notes: - Schema is designed to align with ADR-0128 requirements (required fields + retention constraints). - This PR does not change controller behavior; it only emits events when other components call AuditEmitter.emitAutoAction(...). (Behavioral changes live in the controller hook PR.)

Testing: - Unit tests for schema serialization + required fields - Integration test with local event-bus harness validating routing key + consumer compatibility

Rollout: Feature-flagged behind audit.emit_rollout_auto_actions (default off). Enabled in staging in follow-up once Console API consumer is deployed.

Follow-ups: - Wire Console timeline UI to decision_correlation_id filtering (ENG-4833) - Add alert routing to include decision_correlation_id in Slack notification (ENG-4872)
