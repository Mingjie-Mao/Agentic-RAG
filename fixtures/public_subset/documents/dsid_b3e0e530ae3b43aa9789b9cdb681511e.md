Add RBACv2 explainability service, audit correlator, and KMS consent cache

Context: customers and security reviews asked for better explainability for RBACv2 decisions and stronger correlation between RBAC decisions and audit logs. This PR adds a small, opt-in RBACv2 Explainability service that returns human-friendly decision traces, an audit correlator that links policy decisions to persisted audit events for incident investigation, and a lightweight in-memory KMS consent cache to accelerate residency/consent checks during policy evaluation. Design notes: the explainability service exposes a read-only HTTP endpoint used by the Console and CLI; it consumes the same policy decision trace emitted by the PDP and performs redaction of sensitive tokens before presentation. The audit correlator hooks into the audit pipeline and attaches a stable decision_id to audit events (UUID v7) so investigators can look up the exact policy evaluation that produced a grant/deny. KMS consent cache stores short-lived consent proofs (ttl=15s by default) keyed by (tenant, kms-key-hash) and is used strictly as a fast-path for residency/kms origin checks; it is feature-flagged and falls back to online verification. Migration/compatibility: all behavior is guarded behind the feature flag rbacv2_explainability and audit_correlation enabled via operator config; customers on Dedicated/Private can toggle independently. Security: explainability returns only redacted paths and never discloses full encryption context or raw KMS tokens. The KMS cache is ephemeral, encrypted at rest in-memory, and does not persist across restarts. Testing: unit and integration tests added for PDP traces, correlator durability under load, and KMS cache correctness under churn. Rollout plan: staged rollout -- enable behind flag in canary for 24h, smoke tests on policy-heavy tenants, then gradual ramp to 25%/50%/100%. Related work: replaces ad-hoc investigator tools and complements existing audit-signing work (see ENG-6117).
