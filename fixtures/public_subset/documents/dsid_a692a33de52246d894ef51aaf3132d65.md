Epoched fanout controller with stepwise commit and resumeable rollback

Motivation: multi-stage rollouts (canary/A-B/shadow) must make incremental progress in a way that survives controller restarts, supports manual intervention at well-defined epochs, and provides deterministic rollback to the last known-good commit. This PR introduces an "epoched fanout" controller that divides a rollout into discrete epochs (batches) and records an append-only snapshot after each epoch commit. Each epoch snapshot contains routing deltas, traffic weights by cohort, and aggregated metrics checkpoints. Key features: 1) stepwise commit: the controller applies changes in small epochs and only advances the commit pointer after a successful safety gate evaluation; 2) resumeable progress: epoch snapshots are durable in the snapshot store so a controller restart can resume from the last committed epoch without reapplying or double-counting traffic; 3) deterministic rollback: when a safety gate trips, the controller computes a rollback plan that replays the last stable epoch snapshot and issues a coordinated fan-in to the previous routing state; 4) multi-mode support: works for canary, weighted A/B splits, and shadow mirroring (shadow epochs are recorded but traffic is never shifted); 5) dry-run and simulation: an integrated simulator validates epoch boundaries and race scenarios during CI; 6) observability: new rollout_epoch, epoch_commit_latency_ms, fanout_progress_percent, snapshot_age_seconds metrics and structured traces that show epoch state transitions. This description includes high-level design rationale, implementation notes and the test checklist. Implementation notes: - New epoch snapshot store (rollout/epoch_snapshot_store.py) backed by the existing configstore with append semantics. Snapshots are small (~2-6KB) and regularly GC'd by snapshot TTL. - Controller changes (rollout/controller.py): epoch state machine, commit/abort/rollback transitions, deterministic hashing for cohort assignment, and safety gate hooks. - Routing layer adapter (routing/traffic_fanout.go): stepwise apply/rollback helpers and compatibility shims for legacy routing plugins. - Tests (tests/unit/test_epoched_rollout.py, tests/integration/epoched_rollout_sim.py) cover loopback, restart-resume, rollback under metric flapping and shadow-only epochs. - Docs and runbook (docs/runbooks/epoched-fanout.md) with operator playbook for manual recovery and rollback commands. Checklist: - [x] Design doc review (ENG-1892) - [x] Unit tests for epoch transitions - [x] Integration simulation for restart/resume - [x] Metrics and tracing added - [x] Runbook and example rollout YAML - [x] Backwards compatibility verification with legacy routing adapter Known limitations: - The snapshot GC TTL is conservative and may need tuning for very long-running experiments; - Very large numbers of cohorts (>>1000) will still be limited by routing plugin performance (future work: shard-aware fanout). On upgrade: controllers will automatically begin writing epoch snapshots under the existing configstore namespace. To minimize snapshot retention during the first 24h, set rollout.snapshot_ttl to 72h in charts/values-rollout.yaml. If you need to abort mid-epoch, use 'redwoodctl rollout abort --epoch <n>' which replays the last committed epoch snapshot and issues the fan-in plan.
Backward compatible with legacy routing adapters. Adds small persistent metadata per rollout (snapshot records ~2-6KB). Improves reliability for long-running staged rollouts and reduces human intervention in rollback scenarios.
