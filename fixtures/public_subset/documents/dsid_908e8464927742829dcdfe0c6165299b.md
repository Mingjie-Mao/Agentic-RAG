dynamic per-channel requant + KV-aware jitter-resilient continuous-batching

Background and motivation: Production workloads show variance in per-channel activation distributions across prompts and token positions which makes static requant scales suboptimal. We observed systematic p99 latency spikes when the runtime switched between hot and cold KV cache footprints under continuous-batching; these were exacerbated by small batching jitter when multiple streams aligned. This PR implements a dynamic per-channel requant stage combined with a KV-cache-aware scheduling hint and a jitter-resilient continuous-batching policy to smooth throughput while keeping low tail latency. Scope: 1) A lightweight per-channel scale estimator that runs on the microkernel hot path and updates requant multipliers at configurable amortization windows. 2) A cheap, lock-free KV cache sizing hint that the scheduler uses to avoid abrupt prefix evictions during batch coalescing. 3) A jitter-resilient continuous-batcher that introduces minimal, adaptive hold windows to align requests from high-variance sources without increasing median latency. 4) Microkernel changes to expose a fused transform that applies requant multipliers inline with dequant/attn input packing to eliminate an extra copy. Design highlights and tradeoffs: - Estimator runs every N tokens (configurable per model) and uses exponential moving moments to remain stable across bursts. The goal is to reduce per-token compute overhead to <0.5% while adapting scales within 5-10k tokens. - Scheduler hint is advisory: it tags requests with estimated KV working set delta. The placement layer still enforces hard SLOs; the hint avoids placing requests that would cause a working-set jump on the same GPU within a short window. - Batcher employs an adaptive jitter budget: it only delays the head of a queue by up to X ms if the expected throughput improvement outweighs the added latency; X decays if p99 latency rises. Benchmarks (representative): - OPT-13B, INT8 hybrid (smoothquant + per-channel dynamic re-quant): throughput +10.8% on steady-state mixed sized prompts, median latency +2% (due to micro-batching alignment), p99 latency -14% on tail-heavy traces. - Llama-2-7B FP8 fallback: end-to-end token cost reduced by ~7% due to fewer KV evictions and reduced memory copies. - End-to-end e2e test with 500 simulated concurrent streams: observed 8-12% lower GPU-side memcpy time and 6-9% better sustained throughput. Implementation notes: - Runtime changes: src/runtime/quant/dyn_requant.h/cpp, src/runtime/quant/microkernel_requant.s, src/runtime/scheduler/kv_hint_scheduler.cpp - Batcher: src/runtime/batching/jitter_batcher.cpp, with a new config block in configs/batching.yaml - Tests: tests/quant/test_dyn_requant.cc (unit), bench/latency/bench_kv_jitter.py (integration traces) - Docs: docs/perf/quantization.md updated with configuration knobs and suggested Linear tasks for tuning. Checklist: - [x] Unit tests for estimator accuracy and stability - [x] Integration benchmark harness with trace replay - [x] Backwards-compatibility: dynamic requant disabled by default; opt-in via runtime config - [x] Release notes draft included - [x] SRE smoke test run on dedicated cluster and passed Notes on safety and compatibility: This change touches kernel hot-paths; dynamic scaling is guarded behind a runtime flag and tuned conservatively out-of-the-box to avoid regression. We included an automatic rollback condition in the scheduler when p99 exceeds baseline by 20% during an experiment.
