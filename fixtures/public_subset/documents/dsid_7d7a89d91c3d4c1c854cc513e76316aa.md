streaming-session-snapshot-client-ack-add-resume-token-openai-compat

Motivation: Improve streaming resilience for mobile/unreliable clients and make client-initiated cancel behavior idempotent while preserving OpenAI compatibility. This PR introduces a 'streaming session snapshot' model and explicit client ACK semantics so disconnected clients can reconnect and resume without inconsistent tool calls or duplicate function invocations. Includes small API surface additions (resume_token, session_id, seq) exposed in the OpenAI-compatible streaming adapter.

Summary of changes: 1) Protocol: add optional query/header parameters: X-Redwood-Session-Id (UUID), X-Redwood-Resume-Token (opaque token), and X-Redwood-Seq (monotonic integer). Server will emit a resume_token event at checkpoint boundaries (full structured object flush points) to allow resumption. 2) Client ACK semantics: streaming responses now include an ACK event type ("ack") that clients can send to confirm they received the last checkpoint; server holds tool-call/side-effect commits until ACK or until server soft-timeout expires. 3) Idempotent cancel: client-initiated cancel now accepts a cancel-with-reason payload and returns an idempotency token; repeating cancel requests with the same idempotency token is a no-op. 4) Server-side grace window: implement a configurable soft grace period (default 30s) after disconnect where session state and pending tool call fences are retained to allow resume. After grace window expiration the session is garbage collected. 5) Function-calling/structured output: ensure structured JSON blocks are flushed at checkpoint boundaries; add deterministic boundaries to avoid partial structured chunks on reconnect. 6) OpenAI compatibility layer: expose resume_token as a top-level SSE event named "resume_token" and support incoming resume headers for existing SDKs; keep the text/event-stream framing compatible with existing clients.

Why this is different from previous proposals: previous work focused on reconnect/retry-backoff and teardown safety. This PR couples explicit checkpoint metadata and client ACKs to avoid duplicate function calls and to provide a concrete resume point that is safe across network blips. It is optimized for tool calling workloads where side effects must be constrained to once semantics.

Commits (high-level): [1] protocol: add session id and resume token headers and wire through adapter; [2] runtime: checkpoint serializer and resume token generation; [3] runtime: hold-and-commit mechanism gated by client ACK and grace window; [4] api: idempotent cancel endpoint and cancel idempotency token; [5] openai-adapter: SSE event renames and backward-compatible parsing; [6] tests: end-to-end resume and duplicate-cancel tests; [7] docs: streaming lifecycle migration guide and SDK hints.

Files changed (high-level): api/streaming_adapter.py (protocol parsing and headers), runtime/checkpoint_manager.rs (checkpoint persistence and GC), runtime/tool_fence.rs (hold/commit logic), openai_compat/sse_adapter.go (resume_token event), stdlib/net/ack_client.py (SDK helper), tests/integration/test_resume.py, docs/streaming-lifecycle.md.

Testing: added deterministic unit tests for checkpoint boundaries and a flaky-network harness that simulates TCP drops and validates resume semantics across reconnects. End-to-end tests ensure that function-calling side-effects execute exactly once when clients follow ACK/resume contract. Performance: microbenchmark shows ~3% p99 overhead for sessions with frequent checkpoints (configurable), negligible for typical chat flows.

Migration notes: - Backwards compatible: clients that do not send session headers keep existing behavior. Resume support is opt-in (server issues resume_token only when session_id provided). - SDKs: quick helper added in python/ts/go SDKs (std ack helper) and docs updated with example reconnect flow. - Operators: new config runtime.streaming.grace_window_seconds (default 30) and runtime.streaming.max_session_persist (default 10m).

Rollout plan: feature-flag rollout behind 'stream_session_snapshot' flag. Start with internal beta, then enable for hosted customers on request, then GA after 3 weeks of monitoring. Alerts: added SLO-level alert if resumed session failure rate > 1% over 1h.

Known limitations & follow-ups: - Resume requires client to retain resume_token; tokens are opaque and ephemeral. We will later add signed tokens for cross-region resume. - Tool-call fences add memory pressure while session is in grace window; follow-up to add spill-to-disk for very large pending calls (ENG-2210).
