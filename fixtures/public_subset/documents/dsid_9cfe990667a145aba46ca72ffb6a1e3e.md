Ephemeral KMS affinity and audit sanitization pipeline

Background: Customers operating in regulated regions asked for two pain points to be addressed together: (1) ensuring KMS usage is region-affine to tenant data residency policies, and (2) removing sensitive tokens and PII from downstream audit sinks prior to export. Motivation: previous work added KMS region scoping checks at the API surface, but key usage still flowed to global key wrappers in some paths and audit exporters occasionally leaked request-level tokens. This change bundles a defensive, production-ready approach: (A) an ephemeral KMS affinity layer that selects tenant-scoped, region-bound keys for short-lived operations and records deterministic key-tag metadata; (B) an audit-sanitization pipeline that applies attribute-aware redaction rules before any logs or audit events are published to external sinks.
What this PR does (concise):
- Adds a KMS Affinity evaluator (policy-driven) that resolves key candidates based on tenant attributes, data residency tag, and RBAC v2 attribute checks. The evaluator returns a short-lived key handle (ephemeral KMS token) and emits sealed metadata to the audit subsystem.
- Introduces an audit-sanitizer stage in the audit forwarder that: 1) removes bearer tokens and secrets from headers/metadata; 2) normalizes and redacts user-identifiable fields (email, phone, SSN-like patterns) using configurable regex rules; 3) annotates events with non-sensitive geotags (region-only).
- Adds RBAC v2 enforcement hooks so key selection requires the caller to possess both the key:use permission and the attribute:kms_region match for targeted tenants.
- Adds unit and integration tests for the affinity evaluator and sanitizer (including regression tests for previously-leaked path).
- Updates documentation (security/rbac.md and audit/exporter.md) and adds an operational guide for enabling sanitizer rules on a per-tenant basis.
Rollout plan: feature gated behind "security.ephemeral_kms_affinity" and "audit.sanitizer_v2" flags. Step 1: enable in staging and run log-compatibility job against internal sinks. Step 2: enable for a small set of low-volume tenants behind canary. Step 3: full rollout once metrics (no increased error rate, <0.1% sanitizer-induced drops) are green.

Notes/Limitations: - The sanitizer uses heuristics for PII detection; customers with strict legal obligations should review rules and may opt to route raw audit streams to internal sinks only. - Ephemeral KMS tokens are short-lived (5m TTL) and rely on internal caching to avoid QPS spikes; autoscaling of the KMS proxy is included as an operator note in the rollout guide.
