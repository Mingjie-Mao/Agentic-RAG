Continuation-token resume and inflight-abort coordination; tool idempotency and structured-output safety for OpenAI compatibility

Context and motivation: production customers hit two classes of failure during network blips: (1) client-initiated aborts that left short-lived partial server state and occasionally caused duplicate tool invocations after reconnect, and (2) reconnect/resume attempts that had no safe, compact representation to resume streaming output without re-executing model/tool side-effects. This PR implements a continuation-token based resume protocol, coordinated inflight abort draining, and safeguards to ensure function/tool calls are idempotent across resume. Design highlights: (a) resume token: server issues a short, opaque continuation token (base64) at consistent milestones (end-of-chunk boundaries). Clients may present X-Redwood-Resume: <token> or ?resume_token=<token> on new stream connections to pick up where they left off. Token encodes minimal offsets (model position, KV-cache fingerprint, and deterministic tool-invocation watermark) plus a short TTL. (b) inflight-abort coordination: client soft-abort now sends a Cancel-Request that triggers a two-phase drain: server stops emitting new tool calls, finishes deterministic local generation up to last checkpoint, and returns a resumable token. If client hard-aborts (disconnect without Cancel-Request), server continues a short grace-window (configurable per-customer) to finish checkpointing before force-cancel. (c) tool idempotency: we attach stable invocation-ids to function/tool calls and persist a compact invocation journal keyed by model run + invocation-id. On resume, server checks the journal and will not re-run tool side-effects; instead a cached tool result or a deterministic no-op response is returned. (d) structured-output validation: added an optional resume-aware JSON repair step that verifies structured outputs (tools or JSON schema) across resume boundaries and emits a delta warning if schema drift is detected. (e) OpenAI compatibility: request/response changes are additive; compat layer accepts X-Redwood-Resume or the resume_token param, and falls back to current behaviour when absent. Backwards compatibility: tokens are optional; clients that do not opt-in see identical semantics as before. Implementation notes: touched server streaming orchestration, control plane resume token signer/verifier, a compact durable journal implemented in storage/streaming/journal.go, and client-facing docs and SDK helpers in redwood-sdk-typescript and redwood-sdk-python. Testing and CI: added unit tests for token roundtrips, journal replay, and tool-invocation dedup; integration tests simulate flaky TCP networks and reconnect flows; a small perf microbenchmark shows ~3% CPU overhead under typical conversational workloads when journalling enabled. Rollout: feature gated behind "stream_resume" runtime flag and a per-tenant grace-window config. Migration: no migration necessary for persisted models; operators can enable incrementally for customers. Risks and mitigations: journal growth is bounded by TTL + config; we added a compaction job and an optional size cap per-tenant to avoid unbounded storage. Security: tokens are signed with kube-managed keys and include short TTLs to reduce replay risk. The PR includes docs and SDK helpers for clients to adopt resume semantics.
Added opt-in streaming resume via continuation tokens (X-Redwood-Resume / resume_token). Ensures safe resume semantics and prevents duplicate tool invocations by persisting a short-lived invocation journal. Feature is behind a runtime flag 'stream_resume' and is off by default. Added SDK helpers in TypeScript and Python and streaming resume docs.
Gate behind 'stream_resume' feature flag. Start with canary on 5% of tenant traffic, run compaction/monitoring job, then ramp to 50% then 100% if stable. Monitor metrics: resume_success_rate, resume_replay_skips, journal_size_per_tenant. If journal growth exceeds threshold, fallback to non-resumable mode for that tenant and create support ticket.
Continuation tokens are signed and include TTL; key rotation handled via control-plane KMS. Journal entries are tenant-scoped and obfuscated; no model weights or sensitive intermediate plaintexts are persisted.
