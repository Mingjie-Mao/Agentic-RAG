introduce-kernel-backpressure-span-linker-and-batch-cost-attribution

Context and motivation: We currently surface token-level cost and latency breakdowns but lack visibility into GPU kernel-level backpressure and how cost accumulates across batches. Teams were blind to 'hidden' latency introduced by kernel serialization and memory-pressure spikes during mixed-model workloads. This PR introduces kernel backpressure span linking, a deterministic per-batch cost attribution pipeline, and corresponding dashboard+alerting to help SREs and runtime engineers diagnose and cap cost/latency regressions.

What this PR does (high level):
- Add OTEL span enrichment for kernel events (attributes: kernel_name, kernel_queue_depth, kernel_queue_ms, gpu_active_ms, memory_bytes_reserved). Spans are linked to invocation batches via a new deterministic batch_id tag.
- Implement a lightweight span-linker in the serving runtime that emits a batch lifecycle span (batch.begin, batch.exec, batch.finish) and attaches kernel child spans with precise timestamps.
- Compute per-batch GPU-time cost and attribute it down to individual invocations in the batch using token-weighted attribution and a configurable per-GPU-cost-rate. This output is written to the telemetry pipeline as compact metrics and a rollup table for ad-hoc queries.
- New dashboards: "Batch Cost Waterfall", "Kernel Contention Timeline", "Per-model Memory Pressure sparkline" (Grafana). Dashboards include drilldowns that link directly to sampled traces for the offending batch_id.
- Alert tuning: add kernel-backpressure-high (SLO impact candidate) that triggers when kernel_queue_ms p50 > X for > 5min or when batch_gpu_cost p99 spikes by > 3x for same window. Alert suppressions added to avoid noisy short spikes (dampening with 5-minute evaluation).

Review conversation summary:
- Jonah Park: asked for defensiveness when batch_id cannot be generated (e.g., preflight failures). I added a fallback to a synthetic id and explicitly mark synthetic in span attribute so downstream can ignore if desired.
- Priya Natarajan: requested clarification on attribution when token counts are missing (e.g., streaming tool calls). We added a fallback proportional attribution by predicted output length and documented the bias in runbook.
- Leo Alvarez: flagged potential cardinality explosion from batch_id if we keep full string. We switched to a compact hex-encoded 8-byte batch_id and added a retention policy to drop raw span attributes in high-cardinality tenants; rollups keep aggregated numbers only.
- CI: initial lint failure (formatting), a small follow-up commit reformatted a header and fixed a flake8 complaint. Integration tests flagged a timing flake in test_batch_span_linking; increased test timeout and stabilized the test (added polling-based assertion). Final CI run: all checks passed.

Testing and validation:
- Unit tests: attribution edge cases (zero-token fallback, zero-cost GPUs) covered.
- Integration: end-to-end trace generation registered in test harness and validated that batch spans and kernel spans are linkable and that rollup ingestion produced expected per-batch cost numbers.
- Staging rollout: deployed to staging traffic for 48 hours; compared per-batch GPU-time computed vs. GPU metrics (nvidia-smi derived) and observed <4% delta for stable models.

Operational considerations:
- Backfilling: migration script populates rollups for the last 7 days; long-term historical data will be sparse and is not a blocking issue.
- Cost namespaces: per-tenant config allows disabling per-batch rollups for low-volume tenants to avoid extra storage cost.
- Alert tuning: we opted for conservative thresholds initially and will adjust after 2 weeks of production telemetry.
