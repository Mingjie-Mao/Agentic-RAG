tool-result-merge-policy-and-exponential-backoff-for-parallel-calls

Summary: Introduces a configurable tool result merge policy and a per-invocation exponential backoff/retry budget aimed at improving ergonomics and determinism for parallel/multi-tool calls. Motivation: the previous default (inject-first-returned) caused nondeterministic structured-output injection when multiple tools returned overlapping JSON fragments or produced idempotent but out-of-order updates. This led to subtle regressions in downstream parsers and customer incidents (SUP-9021). Design: add three merge strategies: first_wins (legacy), last_wins, and merge_patch (depth-aware JSON/struct merge that preserves keyed identities and deduplicates array items when an id key is present). Merge order is deterministic by explicit priority then monotonic timestamp. Implement a per-call RetryPolicy that exposes base_delay_ms, factor, max_attempts, max_delay_ms, jitter_pct and an overall retry_budget_ms to avoid retry storms that starve streaming tokens. The runtime applies exponential backoff with jitter and a budget check before scheduling retries; when budget is exhausted we surface a partial-injection event and optionally trigger a fallback model or canned response based on caller policy. API surface: ToolInvocationOptions gains result_merge_policy and retry_policy fields. OpenAI compatibility: map legacy tool_call behavior to result_merge_policy=first_wins by default and emit a single deprecation notice per workspace when user libraries request explicit tool_call hints. SDKs: TS/Python/Go helpers to opt-in and a migration linter rule that flags ambiguous tool call patterns. Rollout: default behavior remains first_wins to preserve backwards compatibility; merge_patch is enabled behind a gate and will be rolled out to 10% traffic for initial experiments. Observability: new metrics added tool_result_merge.policy{policy} count, tool_result_merge.conflicts, tool_result_merge.resolved_by and retry metrics retries_per_invocation and retry_budget_exhausted. Dashboards updated under "Tooling / Result Merge" to show conflicts over time and the fraction of calls that used merge_patch. Testing: unit tests for conflict resolution, array deduping, id-key heuristics and integration tests that simulate 3 parallel tool calls with conflicting ids and transient failures. Performance: microbenchmarks show a median 7-12% extra CPU latency on 3-way merges with merge_patch but end-user parser error rate drops by 18-42% depending on workload. Backwards compatibility: no breaking change by default; customers can opt into alternate policies per-route or globally. Docs: added migration guide and examples showing how to express merge policies for common tooling patterns. CI/QA: initial CI run failed lint and a flaky time-sensitive test; fixed by mocking monotonic clock and adding unit test coverage for jitter. Merge and deployment: feature-flagged implementation, gradual ramp to 100% after 2-week smoke window, emergency kill switch in Console. Related work: ties to ENG-2431 and earlier speculative affinity work; addresses SUP-9021 incident. See commits for implementation details and changed files for exact locations of changes.

This PR is intentionally conservative: default is legacy behavior to avoid breaking users. The implementation is feature-flagged and rollout is gradual. We measured correctness improvements in end-to-end parser tests which motivated prioritizing this change over low-latency micro-optimizations. The team will follow up with a smaller perf-optimization PR that trades some CPU for lower median latency when merge_patch is used.
