Policy engine: deterministic failover signal hierarchy evaluation + config schema

## Summary
This PR implements deterministic evaluation semantics for failover trigger signals in the policy engine and introduces a versioned config schema to express signal priority, corroboration requirements, and anti-flap dampening inputs. The goal is to eliminate ambiguous/unstable decisions under noisy signals (false positives) and to make controller recommendations reproducible across replicas and over time.

This is a core building block for the Regional Failover Automation Upgrade (Reliability Program). It aligns with ADR-042 (failover trigger signal hierarchy) and is intended to be consumed by the failover controller (dry-run + execution) and by routing decisioning for Hosted API + Dedicated.

## Motivation / problem
Today the policy engine effectively evaluates “best effort” based on whichever signal arrives first and the order of predicates in config. Under partial outages, slight differences in signal availability (or timestamp skew) can lead to:
- non-deterministic policy flip recommendations across replicas
- oscillation between regions when signals conflict
- hard-to-audit decisions (no consistent ‘why’ path)
- inability to safely validate dry-run recommendations against a recorded signal snapshot

## What changed
### 1) Deterministic evaluation pipeline
- Added `SignalHierarchyEvaluator` which produces a stable decision outcome for a given set of signals + config.
- Evaluation is explicitly ordered by configured priority (highest authority first), with deterministic tie-breaking.
- The evaluator produces a structured `DecisionTrace` capturing which signals were considered, which were missing/stale, and which rule fired.

Determinism rules:
- Signals are normalized and sorted by `(priority_rank, signal_type, region, source)`.
- Only signals within freshness windows participate (defaults, override per signal type).
- If a high-authority signal is present and crosses threshold, lower-priority signals cannot override it; they can only corroborate or contribute to confidence.

### 2) Config schema update (versioned)
Introduced `signal_hierarchy` config stanza with `version: v2` behind a feature gate; the legacy interpretation remains default.

New schema concepts:
- `priority_order`: an explicit ordered list of signal classes (e.g. `reachability`, `http_5xx_burn`, `tail_latency_burn`, `capacity_exhaustion`).
- `corroboration`: optional rules requiring a second signal to confirm before declaring a region impaired, except for “authoritative” signals.
- `freshness`: per-signal TTLs and maximum allowed staleness.
- `hold_down_inputs`: evaluator emits the recommended hold-down metadata (it does not enforce timers itself; enforcement stays with the controller/guardrails layer).

Default v2 order (per ADR-042): reachability > 5xx burn > tail latency burn > capacity exhaustion.

### 3) Policy predicate API changes
- Added `evaluate_with_trace()` for consumers that need audit/UX (controller dry-run, incident-bot summaries).
- Kept `evaluate()` intact, implemented as a thin wrapper that discards trace.

### 4) Unit tests + fixtures
- Added golden tests for deterministic traces given identical recorded signal snapshots.
- Added edge case tests:
  - missing signal streams (should not crash; should degrade to “insufficient evidence”)
  - stale reachability vs fresh burn-rate (ensure stale signal cannot block)
  - conflicting signals across regions (stable winner selection)
  - corroboration requirement satisfied/unsatisfied
  - tie-breaking stability across map iteration order

## Backwards compatibility / rollout
- Default behavior is unchanged unless `signal_hierarchy.version: v2` is set for a route/tier.
- The evaluator emits trace fields that are safe for internal logs (no customer payloads).
- This PR does not change controller behavior directly; it only provides deterministic evaluation + schema.

Recommended rollout plan (tracked in ENG-2412):
1) Enable v2 in staging for a limited set of routes and compare decisions vs legacy mode (diff tool in follow-up).
2) Turn on dry-run in prod for a limited tenant allowlist; emit audit events only.
3) Once confirmed, allow v2 default for multi-region routes.
