Traffic-gate cascade and deferred rollback protocol for staged lifecycles

Summary: Implements a Traffic-Gate Cascade controller and a Deferred Rollback protocol to improve safety for staged model rollouts. The controller sequences traffic gates across dependent deployment slices (canary -> staggered cohorts -> general pool) and introduces a deferred rollback window that allows transient anomaly mitigation without immediate destructive rollbacks.
Motivation: We observed oscillation during a recent multi-cohort canary (ENG-2148) where immediate automatic rollback on short-lived metric spikes caused repeated flaps. This PR implements a middle ground: hold a rollback decision for a configurable quiesce window, surface mitigations (rate-limit, temporary shadow drain, feature toggle), and only execute rollback if the anomaly persists or escalates.

Key behaviors introduced (high level): 1) Traffic-Gate Cascade: new CRD-style policy that encodes a DAG of gates. Each gate exposes: target cohort, success/fail metric anchors, min-duration, hold-window, and escalation actions. On pass it advances downstream gates; on fail it enters failure handling.
2) Deferred Rollback Protocol: when a gate fails, controller will: a) mark gate "quiescing" and start a deferred_rollback timer (configurable, default 10m) b) emit advisory alerts and create a transient mitigation suggestion (e.g., reduce canary weight by 20%, enable lossy-sampling) c) if human ACK or automated mitigation resolves signals, controller resumes; otherwise, at timer expiry it executes configured rollback (gradual swap or snapshot revert)
3) Safety hooks: - automatic snapshot of serving plane at gate entry - replayable traffic snapshot for rapid repro - integrated tenant-aware rate limit reduction action
4) Handoff quiesce: supports safe pass-through for cohorts with session affinity by draining new sessions and letting in-flight sessions finish before weight adjustments

Note on safety: We intentionally made the deferred window configurable and defaulted to a conservative 10m to balance quick recovery with preventing flapping. We also added an emergency bypass: if a severe SLO breach is observed (configured per rollout), controller may short-circuit the quiesce window and initiate immediate rollback.

Long-form rationale and alternatives considered: - Immediate rollback (status quo) is simplest but caused oscillations in multi-cohort experiments. - Passive mitigation (observe only) reduces churn but requires manual ops. Deferred rollback with automated mitigations provides a middle path that preserves availability while surfacing resolution paths.
Known limitations: - Deferred windows introduce complexity for teams that expect immediate rollback; guidance doc added to explain trade-offs. - Interaction with external rate-limiter plugins may require adapter changes; created follow-up task ENG-2214.
