Add sequenced rollback orchestrator and terraform plan signer

Motivation: Private deployments need deterministic, auditable rollback semantics that are safe across a mix of Helm release updates and Terraform state changes. Existing rollback helpers were ad-hoc (operator hooks + manual DB restores) and insufficient for multi-step upgrades that touch schema, secrets, or network configuration. This PR introduces a sequenced rollback orchestrator that models upgrade steps as reversible phases and a Terraform plan signer which binds a plan snapshot to an upgrade epoch for safe verification and automated rollback verification.

What this PR does (summary):
- Adds a rollback orchestrator service (installer/operator/rollback_orchestrator.py) implementing a finite-state machine for upgrade phases: PREPARE -> APPLY_INFRA -> APPLY_HELM -> MIGRATE_SCHEMA -> VALIDATE -> FINALIZE. Each phase exposes compensating actions and idempotent abort behavior.
- Introduces Helm lifecycle job templates that integrate with the orchestrator via release annotations and an ephemeral release-lock ConfigMap.
- Adds terraform plan signing: before applying any terraform changes, the plan is saved, hashed, and signed by the operator using a cluster-bound signing key; the signer ensures the applied terraform plan matches the expected plan during replay/rollback.
- Adds a small signing shim (terraform/tools/plan_signer.go) and CI guard (ci/terraform/verify_plan_signatures.sh) to validate plans in CI and operator runtime.
- Migration helper utilities that snapshot DB-compatible migration state and register verification callbacks into the orchestrator.

Operational notes and safe rollout guidance:
- This change introduces a new CustomResourceDefinition (CRD). Operators should run a migration job on clusters that already have private-installer installed. A compatibility mode exists (ORCHESTRATOR_MODE=passive) allowing operators to opt-in and shadow-run without enforced rollbacks.
- Terraform plan signer requires a plan snapshot artifact store (S3/GCS/MinIO). Administrator must configure installer.options.planSnapshotStore and provide credentials.
- Recommended rollout: enable passive mode for 2 weeks, run a rehearsal (see docs) to collect rollback metrics, then flip to active mode.

Notes on differences from prior work: This PR focuses on binding infra changes (terraform plans) to application-level rollbacks through signatures and explicit sequencing. Prior PRs added preflight checks and snapshotting; this one creates a runtime orchestrator and cryptographic binding for plans so that rollbacks can assert the infra state they expect before applying compensating actions.

Upgrade/rollback example (short):
1) Operator creates Rollout CR and stores signed terraform plan snapshot with epoch id E-20250118-001.
2) Orchestrator applies APPLY_INFRA -> verifies plan signature then proceeds.
3) Helm releases applied (APPLY_HELM).
4) Schema migrations run (MIGRATE_SCHEMA). During validation, a mismatch is detected. Orchestrator triggers compensation for MIGRATE_SCHEMA then APPLIED_HELM and finally triggers terraform revert using the earlier signed plan snapshot.
